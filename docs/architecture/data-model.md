# Monitoring domain model

## Purpose

This document defines the relational monitoring domain that must exist before
agent protocol, synchronization and probe execution work begins. It deliberately
does not finalize the TimescaleDB measurement schema; that is a separate Stage 0
decision built on the identities and relationships established here.

All models in this document are realm-owned and follow
`docs/architecture/tenancy.md`.

## Relationship overview

```text
Realm
  |
  +-- AgentGroup -- AgentGroupMembership -- Agent
  |                                        |   |
  |                                        |   +-- AgentCredential
  |                                        |   +-- AgentConfiguration
  |                                        |
  +-- TargetGroup -- TargetGroupMembership -- Target
  |                                            |
  |                                            +-- Monitor
  |                                                  |
  |                     +----------------------------+
  |                     |
  |                     +-- MonitorAgentAssignment -- Agent
  |                     +-- MonitorAgentGroupAssignment -- AgentGroup
  |
  +-- Observation <---- Agent + Monitor
          |
          +-- Measurements (TimescaleDB design)
```

The key distinction is:

- a target describes **what destination exists**;
- a monitor describes **how and when it is observed**; and
- direct and group assignments describe **which agents perform that monitor**.

This permits one monitor to run from many vantage points without duplicating its
probe configuration.

## Shared model conventions

Realm-owned relational models use:

- UUID primary keys generated by the application;
- explicit non-null `realm_id`;
- timezone-aware `created_at` and `updated_at` timestamps;
- database constraints for scoped uniqueness where practical; and
- an optional `archived_at` timestamp for resources whose identity must remain
  available to historical observations.

Externally visible resources do not use mutable names as identifiers. APIs and
future Terraform state store UUIDs. Names remain editable display values.

Optimistic concurrency should be exposed through an integer revision or HTTP
entity tag before declarative configuration clients are supported. Stage 3 need
not implement a Terraform provider, but it must not make safe drift detection
impossible.

## Agent

An agent represents one enrolled monitoring installation at a network vantage
point.

Proposed fields:

```text
id                  UUID primary key
realm_id            UUID, required
name                string, unique within realm
description         nullable string
enabled             boolean
archived_at         nullable timestamp
created_at          timestamp
updated_at          timestamp
```

The agent's reported hostname, version, platform, architecture, capabilities and
last-seen time are operational state rather than user-authored identity. Their
exact persistence belongs to the agent-protocol design.

`online` must not be stored as a manually toggled boolean. It is derived from
the latest trusted heartbeat and a documented freshness threshold. An agent can
therefore be enabled but offline, or disabled but recently connected.

Archiving an agent revokes or disables its credentials, removes it from future
configuration and preserves its identity for historical observations.

## Agent group

Agent groups organize monitoring vantage points and allow monitors to be
assigned to a maintained set of agents.

Proposed fields:

```text
id                  UUID primary key
realm_id            UUID, required
parent_id           nullable UUID to another agent group
name                string, unique among siblings within realm
description         nullable string
enabled             boolean
archived_at         nullable timestamp
created_at          timestamp
updated_at          timestamp
```

Groups are hierarchical from the beginning. Examples include:

```text
United Kingdom
  +-- London
  +-- Manchester

Private
  +-- Home
```

An agent may belong to several groups through `AgentGroupMembership`. Membership
is explicit rather than storing one `group_id` on the agent, so location,
environment and operational groupings do not compete for one field.

Proposed membership fields:

```text
id                  UUID primary key
realm_id            UUID, required
agent_group_id      UUID, required
agent_id            UUID, required
created_at          timestamp
```

`(realm_id, agent_group_id, agent_id)` is unique. Parent and child groups and
memberships must remain inside one realm. Group services must reject cycles;
recursive hierarchy queries also need a documented maximum depth or equivalent
protection against pathological trees.

Disabling a group suppresses assignments made through that group without
disabling its agents or erasing membership. Archiving a group disables its
assignments and removes it from normal selection while preserving historical and
audit context.

## Agent credential

Agent authentication material is separate from `Agent` so credentials can be
rotated and revoked without replacing agent identity.

Proposed relational fields:

```text
id                  UUID primary key
realm_id            UUID, required
agent_id            UUID, required
name                string
credential_hash     string, never the raw credential
created_at          timestamp
last_used_at        nullable timestamp
expires_at          nullable timestamp
revoked_at          nullable timestamp
```

The final credential format and enrolment exchange remain Stage 0 protocol
questions. Raw credential material is returned only at issuance and is never
available through a normal read API.

## Target

A target is a reusable named network destination. Its address is deliberately
probe-independent so the same target can have ICMP, HTTP, TCP, DNS and TLS
monitors.

Proposed fields:

```text
id                  UUID primary key
realm_id            UUID, required
name                string, unique within realm
description         nullable string
address             string
enabled             boolean
archived_at         nullable timestamp
created_at          timestamp
updated_at          timestamp
```

`address` is a hostname, IPv4 address or IPv6 address. It does not contain a URL
scheme, path or query string. HTTP scheme/path, TCP port, DNS resolver/query type
and TLS options belong to monitor configuration.

Address syntax is validated, but DNS resolution does not occur when saving a
target. Resolution happens at the agent vantage point so split-horizon DNS and
location-dependent results remain observable.

Two targets may intentionally use the same address under different names. Only
the target name is unique within a realm.

## Target group

Target groups organize destinations for navigation, dashboards and future bulk
operations. They do not implicitly create monitors or copy probe configuration.

Proposed fields:

```text
id                  UUID primary key
realm_id            UUID, required
parent_id           nullable UUID to another target group
name                string, unique among siblings within realm
description         nullable string
archived_at         nullable timestamp
created_at          timestamp
updated_at          timestamp
```

Targets belong to any number of groups through `TargetGroupMembership`:

```text
id                  UUID primary key
realm_id            UUID, required
target_group_id     UUID, required
target_id           UUID, required
created_at          timestamp
```

`(realm_id, target_group_id, target_id)` is unique. The same cross-realm and
cycle protections used for agent groups apply here.

Target groups are intentionally organizational in V1. Assigning a monitor to a
target group would be ambiguous because each target would need monitor identity,
configuration-revision and lifecycle behavior. Future bulk monitor creation
should create explicit monitors rather than make group membership silently alter
the meaning of one monitor.

## Monitor

A monitor defines a scheduled probe against one target.

Proposed fields:

```text
id                  UUID primary key
realm_id            UUID, required
target_id           UUID, required
name                string, unique within realm
description         nullable string
probe_type          constrained string
interval_seconds    integer
timeout_seconds     integer
configuration       JSON object
enabled             boolean
revision            positive integer
archived_at         nullable timestamp
created_at          timestamp
updated_at          timestamp
```

The V1 `probe_type` values are:

```text
icmp
http
tcp
dns
tls
```

HTTPS is represented by the HTTP probe with an `https` scheme rather than a
separate implementation type.

`configuration` is not arbitrary unvalidated JSON. Each probe type has a strict,
versioned Pydantic schema in the control plane and a matching typed Go contract.
The database JSON representation allows heterogeneous configuration while the
application contract supplies validation and generated API documentation.

The monitor timeout must be shorter than its interval unless the later scheduler
design documents a safe overlapping-execution mode. V1 should default to no
overlapping executions of the same monitor assignment.

Increment `revision` whenever a scheduling or probe-behavior field changes. A
name or description change need not invalidate scheduled configuration unless
those values are included in agent-visible data.

Archiving a target archives or disables its active monitors in the same
transaction. An archived target or monitor cannot be newly assigned.

## Monitor-agent assignment

An assignment connects one monitor to one agent.

Proposed fields:

```text
id                  UUID primary key
realm_id            UUID, required
monitor_id          UUID, required
agent_id            UUID, required
enabled             boolean
created_at          timestamp
updated_at          timestamp
```

`(realm_id, monitor_id, agent_id)` is unique. The domain service verifies that
the realm, monitor, target and agent match before writing the assignment.

The explicit assignment model leaves room for future per-agent scheduling or
probe overrides. V1 does not add an unvalidated override JSON field before a
real override requirement exists.

Assignments may be hard-deleted because observations identify the monitor,
agent and applied configuration rather than depending on the assignment row.
Deleting an assignment stops future scheduling but does not delete history.

## Monitor-agent-group assignment

A group assignment connects one monitor to every eligible member of one agent
group.

Proposed fields:

```text
id                  UUID primary key
realm_id            UUID, required
monitor_id          UUID, required
agent_group_id      UUID, required
enabled             boolean
created_at          timestamp
updated_at          timestamp
```

`(realm_id, monitor_id, agent_group_id)` is unique. As with direct assignments,
the domain service validates that all referenced resources share the realm.

The effective agent set for a monitor is the deduplicated union of:

- enabled direct monitor-agent assignments; and
- enabled monitor-agent-group assignments whose group and member agents are
  enabled and not archived.

Nested groups organize the hierarchy but do not automatically include the
memberships of descendant groups in V1. A monitor assigned to `United Kingdom`
runs on agents directly belonging to that group, not implicitly on every agent
in `London` and `Manchester`. This avoids hidden scheduling changes when a group
is moved in the tree. Recursive assignment may be added later only as an
explicit assignment option.

An agent reached by several direct or group paths still receives one assignment
for that monitor. Adding, removing, disabling or archiving a relevant membership,
group or assignment invalidates desired configuration for every affected agent.

Group assignments do not contain probe overrides in V1. Future overrides need a
documented precedence model across direct and overlapping group assignments
before any override fields are added.

## Agent configuration state

The server needs a durable way to determine which desired configuration an agent
should receive and which configuration produced an observation. The detailed
wire format belongs to the agent-protocol document, but the relational design
must support:

```text
agent_id
realm_id
desired_revision
desired_content_hash
acknowledged_revision
acknowledged_at
created_at / updated_at
```

A revision is monotonic for one agent; it does not need to be globally monotonic
across the installation. Any relevant target, monitor, assignment, agent-group
or membership change causes affected agents to receive a new desired revision.

The server should generate configuration deterministically. The content hash
allows it to avoid creating revisions for changes that do not alter agent-visible
behavior.

Full immutable configuration snapshots are persisted server-side as defined in
`agent-protocol.md`. Historical observations identify the applied configuration
revision so their address and probe behavior remain interpretable.

## Observation identity

An observation represents one monitor execution by one agent. It must include at
least these identities regardless of its eventual relational/Timescale layout:

```text
observation_id          client-generated UUID
realm_id
agent_id
monitor_id
monitor_revision
agent_config_revision
scheduled_at
started_at
finished_at
status
```

`observation_id` is generated and durably stored by the agent before upload. The
server enforces uniqueness so replaying an unacknowledged batch is idempotent.

Observations must retain sufficient immutable context to remain understandable
after names, addresses or monitor configuration change. The measurement design
must decide which labels/configuration are snapshotted and which are resolved
from retained revision data.

## Lifecycle and deletion

### Disable

Disabling an agent, agent group, target, monitor or assignment is reversible.
Disabled resources remain visible to authorized users but do not produce new
scheduled work.

### Archive

Archiving removes a resource from normal active lists and prevents reuse while
preserving the identity required for history. Archived names should remain
reserved within their realm and group namespace unless a later product decision
explicitly supports name reuse with clear disambiguation.

### Delete

Permanent deletion is not a normal V1 action for agents, groups, targets or
monitors that have historical or audit references. A later purge workflow may
remove them only after its time-series, audit and retention consequences are
explicit.

Realm deletion follows the resumable administrative workflow required by
`tenancy.md`; it is not an ORM cascade initiated from an ordinary route.

## Configuration API implications

The dashboard, import/export tools and a future Terraform provider must all use
the same management services and APIs.

Required API behavior includes:

- deterministic realm-scoped list and lookup operations;
- stable UUIDs in responses;
- typed probe-specific configuration validation;
- conflict responses for scoped uniqueness and stale revisions;
- no secret recovery through read endpoints;
- idempotency support for operations likely to be retried; and
- explicit enable, disable and archive semantics.

The API must not expose raw Tortoise models as an accidental long-term contract.
Pydantic request and response schemas form the public contract.

## Stage 3 implementation order

After the remaining Stage 0 documents settle measurements and agent protocols,
implement this domain in the following order:

1. Shared realm-owned and archival model conventions.
2. Agent, agent group, membership and credential identity.
3. Target, target group and membership identity.
4. Monitor models with typed probe configuration schemas.
5. Direct/group assignment services and cross-realm validation.
6. Agent configuration revision state.
7. Observation/measurement schema and TimescaleDB migration.
8. Realm-scoped service and authorization layer.
9. Management and ingestion APIs.

Every persistent change requires a reviewed Tortoise migration. Do not use
`generate_schemas()` as a substitute.

## Decisions delegated to adjacent designs

- Agent credentials, enrolment and full desired-configuration snapshot retention
  are defined in `agent-protocol.md`.
- Observation status/error taxonomy is defined in `measurements.md` and may be
  refined by the versioned agent protocol.
- Probe-specific result storage, TimescaleDB dimensions, indexes and retention
  are defined in `measurements.md`.
- Agent clock-skew and timestamp behavior is shared across `measurements.md`,
  `agent-protocol.md` and `sync.md`.
- Health derivation from observations, heartbeats and missing data is defined in
  `health.md`.
